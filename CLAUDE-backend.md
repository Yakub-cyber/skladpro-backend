# skladpro-backend — инструкция для сессии

Ты работаешь **только с этим репозиторием**. Другие части проекта (веб-кабинет,
мобильное приложение, POS) живут в отдельных репозиториях и в отдельных сессиях.
Не предполагай ничего об их коде и не предлагай правки в них — если задача
упирается в клиент, скажи об этом и остановись.

## Что это

Бэкенд B2B SaaS ERP для оптовой торговли (аналог CloudShop / МойСклад).
Fastify + Node + TypeScript, self-hosted PostgreSQL, сырые SQL-миграции,
своя авторизация с ротацией refresh-токенов, offline-sync по `row_version`,
идемпотентность, подписки, фискализация АТОЛ, вебхуки.

Клиенты (веб, мобилка, POS) ходят сюда по HTTP. Сервер — **источник истины по
учёту**: остаток, себестоимость, долг и деньги считает он, а не клиент.

## Главное правило — учётное ядро

Остаток, себестоимость, баланс контрагента и деньги **выводятся из реестров
движений**, а не хранятся как редактируемые поля.

Реестры — источник истины:
- `stock_movements` — товар
- `settlement_movements` — взаиморасчёты с контрагентами
- `money_movements` — касса и счета

Единственное место, где в них появляются строки, — функция **`post_doc()`**.
Откат — только через **`unpost_doc()`**.

Поля `products.stock`, `customers.balance`, `suppliers.balance` — это **зеркало**
для обратной совместимости со старыми клиентами. Их пишет исключительно
`post_doc()` через `sync_product_mirror` / `sync_party_mirror`. Прямой
`update products set stock = ...` где угодно в коде — ошибка, даже если он
«временный» и «только для миграции».

Витрины для чтения: `v_stock_available`, `v_party_balance`, `v_money_balance`.

Если задача выглядит как «здесь надо быстро подправить остаток» — значит нужен
документ через `post_doc()`, а не подправить.

## Открытые задачи, по приоритету

1. **Снять проверку минуса в `apply_stock` — но не везде.**
   В опте отрицательный остаток нормален: товар физически приехал, приходную
   накладную оператор проведёт вечером. CloudShop, МойСклад и 1С это разрешают.
   Сейчас `apply_stock` кидает ошибку на любом уходе в минус — это неверно и
   расходится с поведением клиентов.

   Разрешить минус: `sales_shipment`, `retail_receipt`.
   Оставить запрет: `transfer_out`, `writeoff` — увезти или списать то, чего
   нет, это ошибка ввода, а не запоздавший приход.

   Побочное: при отрицательном остатке средневзвешенную себестоимость не
   пересчитывать — брать последнюю известную, пока остаток не вернётся в плюс.

2. **`select install_ledger_guard();`** — триггеры, запрещающие прямую запись в
   `stock` / `balance` мимо `post_doc()`. Сначала на тестовой БД + прогон всех
   тестов: падение с кодом `P0009` означает забытый прямой апдейт, найти и
   убрать. Потом на прод. После этого вернуться к старому состоянию физически
   нельзя — это и есть цель.

3. **`unit_factor` в продаже захардкожен в `1`.** Блокирует упаковки: «20 упак»
   должно списывать 20 × factor, а не 20. Таблица `product_units` с полем
   `factor` уже есть. Веб-клиент упаковки уже поддерживает — сервер должен
   принимать `unit_factor` из позиции и не перемножать повторно.

4. **`docId` из `Date.now()` в `customers.ts`** — ретрай задвоит платёж.
   Делать `docId` детерминированным из ключа идемпотентности.

5. **Нет `on conflict` на `insert into docs`** — повторная отправка даёт 500
   вместо 409.

## Как проверять

**«Компилируется чисто» и «218 юнит-тестов зелёные» ничего не доказывают про
учёт.** Все юнит-тесты работают на фейковом пуле (`makeFakePool` в
`test/helpers.ts`) — `post_doc()` в них не выполняется вообще.

Приёмка — только это:

```
TEST_DATABASE_URL=... npx vitest run test/integration
psql ... -f reconcile.sql
```

9 интеграционных тестов должны быть **passed, а не skipped**. Без
`TEST_DATABASE_URL` они молча пропускаются, и «пропущено» — это не «пройдено».
`reconcile.sql` должен вернуть 8 пустых результатов.

Любая правка учёта проверяется **циклом**, а не одной операцией: провели →
распровели → цифры вернулись к исходным. Односторонние тесты пропускают ровно
тот класс багов, который здесь чинили.

## Чего не делать

- Не писать в `stock` / `balance` напрямую, ни при каких обстоятельствах.
- Не добавлять второй путь проводки в обход `post_doc()`.
- Не обрезать балансы нулём (`greatest(0, ...)`): отрицательный баланс — это
  предоплата клиента, законное состояние. Обрезка тихо теряет деньги.
- Не удалять и не переписывать инфраструктуру: авторизацию, sync, подписки,
  фискализацию, вебхуки, GDPR, деплой. Она работает, задача — учётное ядро.
- Не коммитить `credentials/`, `.env`, ключи. При подготовке архива для передачи
  исключать `credentials/`, `.env`, `node_modules`, `dist`, `.git`.
